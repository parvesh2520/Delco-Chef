# Render Deployment Guide

How to run the Delco Chefs API on Render, connected to Neon PostgreSQL and Razorpay (test mode), and point the Android app at it.

Throughout, `<service>` is your Render service name. With `render.yaml` it is `delco-chefs-api`, so the URL is normally `https://delco-chefs-api.onrender.com`. Render adds a suffix if that name is taken, so check the URL Render shows you.

## 1. Architecture

```
Android app (Expo) ──HTTPS──▶ Render web service (Docker, 1 instance)
                                 FastAPI + uvicorn (1 process)
                                 └ in-process worker: notifications outbox, link expiry,
                                   7-day unpaid close, offer timeouts, location flush
                                       │ TLS (sslmode=require)
                                       ▼
                               Neon PostgreSQL (ap-southeast-1)
Razorpay (test mode) ──signed webhooks──▶ POST /api/v1/payments/webhook
Customer's browser ──after checkout──▶ GET /api/v1/payments/razorpay/callback
                                         (confirmed with Razorpay's API before anything is marked paid)
```

- **One instance only.** Background jobs and the live-location buffer run inside the API process. A second instance would run every job twice and split the location buffer; that needs Redis first.
- **Region.** The service runs in **Singapore**, next to Neon (`ap-southeast-1`), to keep database round-trips short.

## 2. Render account setup

1. Sign up at <https://render.com> using **GitHub** login.
2. When asked, let Render access the repository **`parvesh2520/Delco-Chef`**. Render deploys what is pushed to GitHub, so commit and push your changes first.

## 3. Create the backend service (Blueprint)

1. In the Render Dashboard, choose **New → Blueprint**.
2. Pick the repository. Render reads `render.yaml` from the repo root, which:
   - builds `backend/Dockerfile`;
   - uses the free plan in Singapore;
   - health-checks `/health`.
3. Render then asks for every variable marked `sync: false`. Fill them in from section 4. `SECRET_KEY` is generated by Render.
4. Click **Apply**. Render builds the image (about 3–5 minutes) and starts the service.
5. Copy the service URL from the service page (`https://<service>.onrender.com`). If it differs from `delco-chefs-api.onrender.com`, update the following and save (and redeploy where needed):
   - `PUBLIC_BASE_URL` (section 4);
   - `mobile/eas.json` (section 9);
   - the Razorpay webhook URL (section 8).

The Docker start command (in `backend/Dockerfile`) is:

```
uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*' --no-server-header
```

That means:
- one process;
- no reload;
- Render's `$PORT`;
- Render's proxy headers trusted.

`autoDeploy` is off. Deploy from the dashboard with **Manual Deploy → Deploy latest commit**, or let CI call the deploy hook (section 13).

## 4. Environment variables

Set them in **Render → your service → Environment**. Names are exactly what the code reads. Never paste these values into chat, issues or docs.

| Variable | Required | Sensitive | What it is | Where to get it |
|---|---|---|---|---|
| `ENVIRONMENT` | yes | no | `production`. Refuses weak secrets and enables production behaviour. | Set by `render.yaml` |
| `DEBUG` | yes | no | `false` | `render.yaml` |
| `DATABASE_URL` | yes | **yes** | Neon **pooled** URL (host contains `-pooler`), with `?sslmode=require` | Neon Console → your project → **Connect** → "Connection pooling" on |
| `DIRECT_URL` | yes | **yes** | Neon **direct** URL (no `-pooler`), for Alembic migrations | Neon Console → Connect → pooling off |
| `SECRET_KEY` | yes | **yes** | Signs access tokens (JWT, HS256) | Generated by Render. Changing it signs everyone out. |
| `FIELD_ENCRYPTION_KEY` | yes | **yes** | AES key for phones, addresses and documents stored in Neon | **Copy exactly** from your local `backend/.env`. A different key makes existing data unreadable. |
| `HMAC_LOOKUP_KEY` | yes | **yes** | Keyed hash used to find users by phone | **Copy exactly** from your local `backend/.env`. A different key breaks every existing login. |
| `PUBLIC_BASE_URL` | yes | no | `https://<service>.onrender.com`. Razorpay's after-payment redirect points here. | Your Render URL |
| `RAZORPAY_KEY_ID` | yes | no (public id) | `rzp_test_…`. Test keys only; live keys are refused. | Razorpay Dashboard (Test Mode) → Account & Settings → API Keys |
| `RAZORPAY_KEY_SECRET` | yes | **yes** | Razorpay API secret | Same place (shown once; regenerate if lost) |
| `RAZORPAY_WEBHOOK_SECRET` | yes, for webhooks | **yes** | Shared secret that signs webhooks. **Empty = every webhook rejected (400).** | You generate it (section 8) |
| `OTP_PROVIDER` | yes | no | `log` (mock SMS) | `render.yaml` |
| `OTP_LOG_CODES` | demo | no | `true` writes login codes to Render's logs, since there is no SMS provider. Set `false` before real users. | `render.yaml` |
| `RUN_WORKERS` | yes | no | `true`: background jobs in the API process | `render.yaml` |
| `RUN_MIGRATIONS` | yes | no | `false`: migrations are run deliberately (section 6) | `render.yaml` |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | no | no | `3` / `2`: at most 5 connections from the free instance | `render.yaml` |
| `BACKEND_CORS_ORIGINS` | no | no | Browser origins only, e.g. `["https://admin.example.com"]`. The native app needs none. | Leave unset |
| `ACCESS_TOKEN_EXPIRE_MINUTES` / `REFRESH_TOKEN_EXPIRE_DAYS` | no | no | Defaults 15 / 30 | Leave unset |
| `MEDIA_ROOT` | no | no | Default `media`. Wiped on every deploy or restart on the free plan. | Leave unset |
| `GIT_COMMIT` | no | no | Shown at `/version`. On Render, `RENDER_GIT_COMMIT` is used automatically. | Leave unset |
| `LOG_FILE` | no | no | Leave **unset** on Render; logs go to Render's log viewer | Leave unset |

**Variables you may have expected but that do not exist:**
- `JWT_SECRET_KEY` is called `SECRET_KEY`.
- `JWT_ALGORITHM` is fixed to HS256 in code.
- `CORS_ORIGINS` is called `BACKEND_CORS_ORIGINS`.

After changing any variable, click **Save, rebuild, and deploy** (or **Save and deploy**). Render restarts the service with the new values.

## 5. Neon database

- **Two URLs.** The app uses the pooled URL (PgBouncer, many short connections). Alembic uses the direct URL (it needs session-level features).
- **TLS.** Keep `sslmode=require` in both URLs. `channel_binding=require` also works with the bundled libpq.
- **Pool size.** The pool is sized for one small instance: up to 5 connections, recycled every 5 minutes. Idle connections are pinged before reuse, because Neon closes idle ones.
- **Error logs.** Database URLs in error messages are logged without the username and password.
- **Neon autosuspends** an idle compute. The first query after that takes a few hundred milliseconds longer.

## 6. Migration procedure

Current state, checked read-only on 12 Nov 2026: **Neon is at `e66cdf57002d`, the only migration (head). The first deploy needs no migration.**

When a future release adds a migration, run it deliberately from your computer before deploying the new code:

```bash
cd backend
# backend/.env must hold the Neon DATABASE_URL and DIRECT_URL
.venv\Scripts\alembic current      # what Neon has now
.venv\Scripts\alembic heads        # what the code expects
.venv\Scripts\alembic upgrade head # only if they differ, and only after a safety point:
```

Before upgrading, create a Neon branch (Neon Console → Branches → Create branch from `main`, "current point in time"). It is an instant copy to roll back to.

Migrations are written expand-first, so the running (old) code keeps working against the upgraded schema. After upgrading, deploy the new code. Never run `alembic downgrade` against Neon without a reason and a branch.

## 8. Razorpay webhook setup (Test Mode)

1. **Generate a secret** on your computer. Don't share it:
   ```bash
   python -c "import secrets; print(secrets.token_urlsafe(32))"
   ```
2. **In Razorpay**, switch the Dashboard to **Test Mode**, then go to **Account & Settings → Webhooks → Add New Webhook**:
   - **Webhook URL:** `https://<service>.onrender.com/api/v1/payments/webhook`
   - **Secret:** the value from step 1.
   - **Active events:**
     - `payment_link.paid`
     - `payment_link.expired`
     - `payment_link.cancelled`
     - `payment.failed`
     - `refund.processed`
     - `refund.failed`
   - Save.
3. **In Render**, go to Environment and set `RAZORPAY_WEBHOOK_SECRET` to the same value. Click **Save, rebuild, and deploy**.
4. **Verify with a real test payment:**
   - In the app, subscribe and pay with Razorpay's test UPI `success@razorpay`, or a test card.
   - In Razorpay, open the webhook to see its recent deliveries. Each should show HTTP **200**.
   - In the app, the payment screen switches to *Paid* on its own within seconds, and the subscription becomes active.
   - Read-only check in the Neon SQL editor:
     ```sql
     select event, outcome, received_at from payment_events order by id desc limit 10;
     ```
     Expect `paid`. A redelivery shows `duplicate`.
   - Repeat with `failure@razorpay`: you should get the `failed` outcome, a *Payment failed* notification, and **Retry payment** in the app.
5. **What a response means:**
   - **400** (`WEBHOOK_SIGNATURE_INVALID`): the dashboard secret and `RAZORPAY_WEBHOOK_SECRET` differ, or the secret isn't set.
   - **200** `{"status": "unknown_link"}`: the event isn't for one of this database's payment links.

Calling the webhook URL by hand proves only that the URL is reachable. A request without Razorpay's signature is correctly rejected. Real verification is a delivery from Razorpay.

**Security properties (unchanged by this deployment):**
- The raw-body HMAC is checked with a constant-time comparison.
- The unique event id makes duplicates no-ops.
- Out-of-order and late events are handled.
- A browser redirect is confirmed with Razorpay's API before anything is marked paid.
- Only the needed payload fields are stored.

## 9. Expo app API configuration

- **Local development:** `mobile/.env` → `EXPO_PUBLIC_API_URL=http://<PC-LAN-IP>:8000/api/v1`, or the emulator address `http://10.0.2.2:8000/api/v1`.
- **Dev or Expo Go session against Render:** set `EXPO_PUBLIC_API_URL=https://<service>.onrender.com/api/v1` in `mobile/.env` and restart `npx expo start -c`.
- **EAS preview and production builds:** `mobile/eas.json` sets `EXPO_PUBLIC_API_URL` and `EXPO_PUBLIC_APP_ENV` per profile.
  - EAS does **not** upload the git-ignored `.env`, so this is the only source in cloud builds.
  - A release build never falls back to a local address.
  - Edit the URL in `eas.json` if your Render URL differs.

**Payment status in the app:**
1. Opening the payment page takes the customer to *Confirming your payment*.
2. That screen polls the server every 4 seconds while it is open.
3. It stops at a final state (paid, failed, expired, refunded) or after 10 minutes, then offers *Check again*.
4. It refreshes immediately when the app returns to the foreground.

Only the server, after the gateway's verified result, can mark a payment paid.

## 10. Android build

```bash
cd mobile
npx eas-cli@latest login                                     # your Expo account
npx eas-cli@latest build -p android --profile preview         # installable APK (internal distribution)
```

1. When the build finishes, open its page on expo.dev and install the APK on the phone. Allow installs from that source.
2. Sign in with a seeded or new phone number.
3. The OTP is in Render's logs: **Logs** → search `DEV OTP`, while `OTP_LOG_CODES=true`.

A new build is needed whenever `eas.json` (the API URL) or native configuration changes. Changes to the backend alone need no new app build.

## 11. Health and version checks

```bash
curl https://<service>.onrender.com/health    # {"status":"healthy","database":"ok","migration":"e66cdf57002d",...}
curl https://<service>.onrender.com/version   # {"version":"1.0.0","commit":"<first 12 of the deployed commit>",...}
```

`/health` returns **503** when PostgreSQL is unreachable, so Render won't route traffic to a broken deploy. Neither endpoint exposes secrets, hosts or stack traces.

## 12. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Deploy fails: `Refusing to start in production with development secrets` | `SECRET_KEY`, `FIELD_ENCRYPTION_KEY` or `HMAC_LOOKUP_KEY` is missing or still a placeholder |
| Deploy fails: `Sandbox gateway is development-only` | `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` not set |
| Deploy fails: `Only Razorpay TEST keys are allowed` | A live key was used; use the `rzp_test_` key |
| `/health` shows 503 `"database":"unreachable"` | Wrong `DATABASE_URL`, missing `sslmode=require`, or Neon project suspended or deleted. The logs show the error with credentials removed. |
| Login works locally but "not found" or wrong data on Render | `HMAC_LOOKUP_KEY` / `FIELD_ENCRYPTION_KEY` differ from the local ones |
| App: "Network Error" or timeout on the first request | The free service was asleep (cold start about 1 minute, longer than the app's 15-second timeout). Retry, or wake it by opening `/health` in a browser. |
| No OTP | Render → Logs → search `DEV OTP`. Requires `OTP_LOG_CODES=true`. |
| Razorpay delivery 400 | Webhook secret mismatch (section 8) |
| Paid on Razorpay but app still pending | Check the webhook deliveries. If the service was asleep, Razorpay retries; the redirect callback also confirms with Razorpay's API. |
| Uploaded photos disappear | Free-plan disk is temporary (section 15) |

## 13. Deploying an update

1. Run the tests locally (`pytest`, `npx tsc --noEmit`). Commit and push to `main`.
2. CI runs the same checks plus the Docker build. If `RENDER_DEPLOY_HOOK` is set in GitHub (repo → Settings → Secrets → Actions), CI triggers the deploy. Find the hook URL in Render → service → Settings → Deploy Hook.
3. Without the hook, use **Render → Manual Deploy → Deploy latest commit**.
4. If the release has a migration, run it first (section 6).
5. Check `/health`, and check that `/version` shows the new commit.

## 14. Rollback

- **Code:** go to Render → service → **Events**, pick the previous successful deploy, and click **Rollback**.
- **Schema:** this is rarely needed, because migrations are expand-first and the previous code runs on the new schema. If needed, run `alembic downgrade -1` from your computer with `DIRECT_URL`. If data is damaged, restore from the Neon branch you made before migrating.
- **Configuration:** fix the variable in Environment, then **Save and deploy**.

## 15. Render free-tier limitations

- **Sleeps after about 15 minutes idle.** The next request waits about 1 minute.
  - Razorpay webhooks that arrive while it sleeps may time out. Razorpay then retries, and the event-id deduplication makes the retry safe.
  - Background jobs (link expiry, the 7-day unpaid close, chef offer timeouts) don't run while it sleeps. They catch up when it wakes, because they compare stored times.
- **0.1 CPU and 512 MB RAM.** Fine for a demo, slow under load.
- **Temporary disk.** Uploaded selfies, food photos, chef documents and data exports are lost on every deploy or restart. Production needs object storage (S3 or R2 with signed URLs) or a paid persistent disk.
- **Monthly hours.** About 750 free instance hours per month across all free services.
- **No pre-deploy command and no shell** on free. Migrations are run from your computer (section 6).
- **No WebSockets are used.** Live location uses HTTP polling, so this is not a constraint.

**Recommended for a real demo or pilot: the Starter plan (about US$7/month).** It is always on, so webhooks are prompt, jobs run on time and there are no cold starts. It also allows a persistent disk or pre-deploy migrations. Nothing in the code requires it.

## 16. Security checklist

- [ ] `ENVIRONMENT=production` and `DEBUG=false`.
- [ ] `SECRET_KEY`, `FIELD_ENCRYPTION_KEY` and `HMAC_LOOKUP_KEY` are set; the last two match the existing data.
- [ ] Razorpay **test** keys only. `RAZORPAY_WEBHOOK_SECRET` is set and matches the dashboard.
- [ ] No secrets in Git (`.env` is ignored) or in the image (`backend/.dockerignore` excludes `.env`, `.venv`, tests, media and logs).
- [ ] CORS is off unless a browser front end needs it. Never use `*` with credentials (the code never allows credentials).
- [ ] Admin and Super Admin APIs require their roles (verified: no token returns 401).
- [ ] Logs redact phones, OTPs (except the deliberate `OTP_LOG_CODES` demo line), tokens and database credentials.
- [ ] Unhandled errors return a generic message; stack traces stay in the logs.
- [ ] `OTP_LOG_CODES=false` and a real SMS provider before any real user signs in.
- [ ] `/api/v1/docs` is public. That is fine for a demo; restrict it before a public launch if wanted.
